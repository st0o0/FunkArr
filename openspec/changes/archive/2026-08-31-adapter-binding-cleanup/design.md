## Context

Both adapter projects manually extract query parameters via `HttpContext.Request.Query["key"]` with inline `int.TryParse` fallbacks. ASP.NET Minimal API supports `[FromQuery]` binding on method parameters and `[AsParameters]` on request records, which handles parsing, nullability, and defaults declaratively.

The NZB generator uses string interpolation to produce XML, encoding title/url as XML comments. This is the only XML producer not using `XmlSerializer`. The NZB spec defines `<head><meta type="...">` for metadata — a standard mechanism that `XmlSerializer` can handle.

## Goals / Non-Goals

**Goals:**
- Use `[FromQuery]` request records for all adapter endpoint parameters.
- Replace NZB string interpolation with `XmlSerializer`-based object model.
- Use spec-compliant `<head><meta>` for NZB metadata instead of XML comments.
- Keep adapters as thin translators (no business logic creep).

**Non-Goals:**
- Splitting the single-endpoint Newznab/SABnzbd dispatch into multiple routes (both specs define one endpoint with mode-switching query params).
- Adding new Newznab/SABnzbd functionality.
- Changing the JSON projection models or DownloadApi response records.

## Decisions

### 1. Request records with `[FromQuery]` over `[AsParameters]` wrapper

Use flat `[FromQuery]` parameters directly on the endpoint lambda, grouped into a request record with `[AsParameters]`. The record captures the full superset of query params for each adapter's single endpoint.

**IndexerApi** — one record for `GET /index/api`:
```csharp
sealed record IndexerRequest(
    [FromQuery(Name = "t")] string? T,
    [FromQuery(Name = "o")] string? O,
    [FromQuery(Name = "q")] string? Q,
    [FromQuery(Name = "offset")] int? Offset,
    [FromQuery(Name = "limit")] int? Limit,
    [FromQuery(Name = "id")] string? Id,
    [FromQuery(Name = "season")] string? Season,
    [FromQuery(Name = "ep")] string? Ep,
    [FromQuery(Name = "tvdbid")] string? TvdbId,
    [FromQuery(Name = "imdbid")] string? ImdbId);
```

**DownloadApi** — one record each for GET and POST:
```csharp
sealed record DownloadGetRequest(
    [FromQuery(Name = "mode")] string? Mode,
    [FromQuery(Name = "name")] string? Name,
    [FromQuery(Name = "value")] string? Value,
    [FromQuery(Name = "start")] int? Start,
    [FromQuery(Name = "limit")] int? Limit);

sealed record DownloadPostRequest(
    [FromQuery(Name = "mode")] string? Mode,
    [FromQuery(Name = "cat")] string? Cat,
    [FromQuery(Name = "priority")] string? Priority);
```

**Why records over individual parameters:** Keeps the lambda signature clean, groups related params, and the record can be passed to handler methods without spreading.

### 2. NZB object model with `<head><meta>`

```csharp
[XmlRoot("nzb")]
sealed class Nzb { Head, File }

sealed class NzbHead { List<NzbMeta> Metas }

sealed class NzbMeta
{
    [XmlAttribute("type")] string Type
    [XmlText] string Value
}

sealed class NzbFile
{
    [XmlAttribute("post_id")] string PostId
    NzbGroups, NzbSegments
}
```

Produces:
```xml
<nzb>
  <head>
    <meta type="title">Some Title</meta>
    <meta type="url">https://...</meta>
  </head>
  <file post_id="1">
    <groups><group>a.b.mediathek</group></groups>
    <segments><segment number="1">FunkArr@news.example.com</segment></segments>
  </file>
</nzb>
```

Serialized via the existing `XmlHelper.Serialize<T>()`. No new serialization infrastructure needed.

### 3. NzbParser reads `<head><meta>` via XmlSerializer deserialization

Instead of line-by-line comment parsing, `NzbParser` deserializes the NZB XML into the same `Nzb` model and extracts title/url from the `Meta` list. The Nzb model classes live in IndexerApi (where they're generated) and are referenced by DownloadApi via project reference — or duplicated as a small internal model since adapters shouldn't reference each other.

**Decision: duplicate the model in DownloadApi.** The NZB model is tiny (5 small classes) and the adapters must not reference each other per architecture guardrails. The DownloadApi only needs the deserialization side.

### 4. Base64 encoding for NZB IDs

The `TryDecodeBase64` and base64 encoding of `title|url` stays as-is in `NzbGenerator`. This is the Newznab `?t=get&id=<base64>` mechanism — unrelated to XML format.

## Risks / Trade-offs

- **[Breaking NZB format]** → Acceptable at 0.x. NZBs are in-flight only (generated by indexer, consumed by download client within the same instance). No persistence.
- **[Model duplication across adapters]** → Small surface (5 classes). Keeps architecture guardrails intact. A shared NZB model project would be over-engineering for this.
