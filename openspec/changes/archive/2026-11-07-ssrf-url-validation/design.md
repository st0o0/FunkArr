## Context

External URLs enter the download pipeline through two paths in FunkArr.ArrApi:

1. **NzbPayload.Decode** — decodes a Base64 JSON payload containing `Url` and `SubtitleUrl` fields. This payload is generated by FunkArr's Newznab search results and later submitted back via SABnzbd `addfile`.
2. **NzbService.FromNzb** — parses uploaded NZB XML and reads `<meta type="funkarr-url">` for the video URL.

Both paths pass the URL through to `DownloadMedia.VideoUrl` and eventually to `FFMpegArguments.FromUrlInput(new Uri(videoUrl))`, which hands it to ffmpeg. No scheme validation exists anywhere in this chain. ffmpeg accepts `file://`, `ftp://`, `gopher://`, and arbitrary `http://` URLs including internal network addresses.

## Goals / Non-Goals

**Goals:**

- Block non-http(s) URLs at the ArrApi boundary before they reach the domain layer
- Cover both `Url` and `SubtitleUrl` fields (both reach ffmpeg)
- Fail gracefully using existing error handling paths (null return from Decode, empty URL in FromNzb)

**Non-Goals:**

- SSRF protection against internal HTTP URLs (e.g., `http://169.254.169.254/`) — would require an IP allowlist/denylist, which is a separate concern
- URL validation in the domain layer — the ArrApi boundary is the only entry point for external URLs
- Changing the NzbPayload format or the NZB XML schema

## Decisions

### Single static validation helper in FunkArr.ArrApi

A static method `UrlValidation.HasAllowedScheme(string? url)` in the ArrApi project. Returns `true` only for `http` and `https` schemes via `Uri.TryCreate` + scheme check. Returns `false` for null, empty, malformed, or non-allowed schemes.

**Why not a shared utility in Core?** The validation is specific to the ArrApi boundary. The domain layer trusts that URLs are already validated. No other project needs this guard.

**Why not throw?** Both call sites already have null/empty handling paths. `NzbPayload.Decode` returns null on invalid input (callers handle this). `NzbService.FromNzb` sets empty URL which `SabnzbdDownloadService.AddFile` rejects. Using existing error paths avoids new exception types.

### Validate at decode/parse time, not at use time

The guard runs when the URL is first extracted from external input, not when it's later used. This ensures no code path can bypass the check, even if new consumers of these URLs are added later.

## Risks / Trade-offs

- **[Risk] Legitimate non-http(s) URLs blocked** → Mediathek CDN URLs are exclusively http/https. No known legitimate use of other schemes. If a future source needs ftp://, the allowlist is a one-line change.
- **[Risk] Partial SSRF remains** → http(s) URLs to internal services (metadata endpoints, internal APIs) are still allowed. Full SSRF protection would require network-level controls or an IP denylist, which is out of scope for this change.
