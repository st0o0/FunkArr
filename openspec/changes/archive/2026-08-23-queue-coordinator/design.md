## Context

The current `DownloadQueueActor` is a monolithic event-sourced actor that handles scheduling (queue order, slot management), download lifecycle (persisting events, starting pipeline), progress tracking, and API responses. Phase 2a extracts scheduling into a dedicated `QueueCoordinator` while keeping `DownloadQueueActor` as the download execution engine temporarily (it gets fully replaced in Phases 2b/2c).

## Goals / Non-Goals

**Goals:**
- Extract queue scheduling (ordering, MaxConcurrent, slot management) into QueueCoordinator
- Route enqueue and lifecycle ops (cancel) through QueueCoordinator
- QueueCoordinator owns its own event-sourced persistence
- DownloadQueueActor becomes a "worker" that receives start commands from QueueCoordinator

**Non-Goals:**
- DownloadRequestTracker (Phase 2b) — QueueCoordinator talks to DownloadQueueActor, not a tracker
- DownloadCoordinator (Phase 2c) — QueueCoordinator starts downloads via DownloadQueueActor, not shard entities
- Heartbeat safety-net (requires DownloadRequestTracker, deferred)
- Pause/Resume (requires Phase 2c failure taxonomy, deferred)
- Priority reordering (deferred to Phase 2c when shard entities exist)

## Decisions

### D1: Transitional architecture — QueueCoordinator wraps DownloadQueueActor

**Decision:** In Phase 2a, QueueCoordinator sits between controllers and DownloadQueueActor. It manages queue ordering and MaxConcurrent, then tells DownloadQueueActor to start downloads when slots are available.

```
Controller → QueueCoordinator.Enqueue(nzoId, url, title, subtitle)
              → persists JobEnqueued, adds to queue
              → TryStartNext(): if slot available:
                  → Tell(DownloadQueueActor, EnqueueDownload(url, title, subtitle))
                  → persists JobStarted

DownloadQueueActor finishes → Tell(QueueCoordinator, JobFinished(nzoId, outcome))
              → persists JobFinished, frees slot
              → TryStartNext()
```

**Why:** This is the minimal cut. DownloadQueueActor continues to work exactly as before for the download pipeline — it just no longer decides when to start. QueueCoordinator decides.

### D2: nzoId generation moves to QueueCoordinator

**Decision:** The nzoId is generated by QueueCoordinator on Enqueue, not by DownloadQueueActor. The controller sends the download payload without a pre-assigned ID.

**Why:** QueueCoordinator needs the nzoId to track the job in its queue. Generating it there keeps ownership clean.

### D3: Separate PersistenceId

**Decision:** `PersistenceId: "queue-coordinator"`. Separate from the existing `"download-queue"` journal.

**Why:** Clean separation. The old journal stays intact for DownloadQueueActor. No migration needed — QueueCoordinator starts with an empty journal.

### D4: GetQueue/GetHistory stay on DownloadQueueActor temporarily

**Decision:** Queue and history queries still go to DownloadQueueActor in Phase 2a. QueueCoordinator only handles scheduling and lifecycle.

**Why:** DownloadQueueActor already has the job details, progress, and history. Moving query handling is Phase 2b (DownloadRequestTracker) scope.

### D5: DownloadQueueActor tracks QueueCoordinator completion

**Decision:** DownloadQueueActor notifies QueueCoordinator when a job completes or fails via a Tell message. QueueCoordinator frees the slot and calls TryStartNext.

**Why:** The completion signal already flows through DownloadQueueActor (it receives MuxOutcome from the pipeline). Adding a Tell to QueueCoordinator is one line.

## Risks / Trade-offs

**[Risk] Two persistence journals for one logical queue** — QueueCoordinator and DownloadQueueActor both persist related events.
→ Mitigation: Temporary state. Phase 2c removes DownloadQueueActor entirely.

**[Risk] Recovery ordering** — After restart, QueueCoordinator replays its events (queue order), but DownloadQueueActor also replays its events (job state). Both need to agree on what's active.
→ Mitigation: QueueCoordinator recovery resets all `_active` to `_queue` and calls TryStartNext, same as the current DownloadQueueActor pattern.

**[Trade-off] Cancel only works for queued jobs** — Cancelling active downloads requires killing the pipeline stream (Phase 2c). In Phase 2a, Cancel removes from queue only.
→ Accepted: Current system also can't cleanly cancel active downloads.
