## Context

FunkArr's Vue.js frontend (Vite + Tailwind) has 12 views, ~40 API endpoints, and 2 SSE streams. Current test coverage is backend-only: xUnit unit tests per domain, ASP.NET TestServer integration tests for API endpoints, and ArchUnitNET for architecture boundaries. The `e2e-verify` skill provides ad-hoc browser verification via `claude-in-chrome` but is not automated or CI-capable.

The UI uses `vue-router` for client-side routing, `vue-i18n` for translations (en/de/de-AT/de-CH), and plain `fetch` + `EventSource` for API communication (no Axios, no Pinia store).

## Goals / Non-Goals

**Goals:**

- Deterministic, fast browser tests that run in CI without Docker
- Full coverage of all 12 views including edge cases (empty states, errors, loading)
- Typed mock data matching actual API response interfaces
- SSE stream mocking for live-transition tests (Activity, Detail, Settings)
- Test interactions: clicks, form inputs, navigation, toast feedback

**Non-Goals:**

- Visual regression testing (screenshot comparison)
- Performance/load testing
- Testing against the real Docker stack (existing `e2e-verify` skill covers this)
- Mobile/responsive layout testing
- Testing i18n for all 4 locales (test with `en`, verify locale switch works)

## Decisions

### 1. Playwright over Cypress/Vitest Browser Mode

Playwright runs real Chromium, supports multiple browsers, has built-in auto-waiting, and excellent CI integration via `npx playwright install --with-deps`. Cypress would also work but Playwright's API is more suited to our test patterns (page object model not needed for this size of app) and the `dotnet-skills:playwright-blazor` skill already exists as reference.

**Why not Vitest browser mode:** It's designed for component-level testing, not full-page E2E flows. We need router navigation, SSE streams, and cross-page interactions.

### 2. MSW (Mock Service Worker) for API mocking

MSW intercepts `fetch` calls at the network level inside the browser. This means our Vue code's actual `fetch` calls are intercepted — no need for dependency injection or test-only API clients.

**Why MSW over Playwright's `page.route()`:** MSW gives us typed handlers that match our TypeScript interfaces, shared fixtures across tests, and the ability to override per-test with `server.use()`. `page.route()` would work but requires more boilerplate per test and can't share typed fixture data as cleanly.

**MSW integration with Playwright:** MSW runs in the browser via a service worker. We register the service worker in a Playwright `beforeEach` by injecting the MSW setup script. The worker file (`mockServiceWorker.js`) is generated by `npx msw init public/`.

### 3. SSE mocking via custom MSW handler + page-side control

MSW doesn't natively support `EventSource` responses. We solve this with a two-part approach:

1. **MSW handler** for `/api/downloads/queue/stream` returns a streaming `Response` with `text/event-stream` content type
2. **Page-side helper** injected via `page.addInitScript()` that patches `EventSource` to emit controlled events

This allows tests to:
- Start with initial queue state
- Push updates (e.g., download completes → item disappears)
- Test the live transition flow deterministically

### 4. Fixture architecture: typed factories, not static JSON

Instead of large static JSON files, we use factory functions that return typed data:

```typescript
// e2e/fixtures/queue.ts
export function makeQueueItem(overrides?: Partial<QueueItem>): QueueItem {
  return {
    downloadId: crypto.randomUUID(),
    title: 'Test.Show.S01E01.GERMAN.1080p.WEB.h264-FunkArr',
    status: QueueStatus.Processing,
    channel: 'ARD',
    category: 'tv',
    ...overrides,
  }
}

export function makeQueueResponse(overrides?: Partial<QueueResponse>): QueueResponse {
  return {
    items: [],
    totalSlots: 2,
    activeCount: 0,
    queuedCount: 0,
    isPaused: false,
    ...overrides,
  }
}
```

**Why factories over static JSON:** Tests can create exactly the data they need. A test for "3 active + 2 queued" just calls `makeQueueItem()` with different `status` values. No maintaining large JSON files that may drift from actual API shapes.

### 5. Test file organization: one spec per view

Each view gets its own spec file. Tests within a file are grouped by concern (rendering, interactions, edge cases). Shared test utilities (fixtures, helpers, MSW setup) live in `e2e/` subdirectories.

### 6. Vite dev server auto-start

Playwright's `webServer` config starts Vite automatically:

```typescript
// playwright.config.ts
export default defineConfig({
  webServer: {
    command: 'pnpm run dev',
    port: 5173,
    reuseExistingServer: !process.env.CI,
  },
})
```

In CI, the server starts fresh. In development, reuses an already-running server for faster iteration.

## Risks / Trade-offs

**[MSW service worker in tests]** The service worker file must be in `public/` and served alongside the app. → Mitigation: Add `mockServiceWorker.js` to `.gitignore` and generate it in the test setup step. Or commit it (it's a standard MSW file).

**[SSE mocking complexity]** Custom EventSource patching is non-trivial and may break if Vue or the browser changes how EventSource works. → Mitigation: Isolate in a single `sse-mock.ts` helper. If it breaks, only one file needs fixing. Alternatively, use Playwright's `page.route()` for SSE endpoints specifically (returns streaming response).

**[Fixture drift]** Factory return types may diverge from actual API responses over time. → Mitigation: Factories import the same TypeScript interfaces (`QueueItem`, `HistoryItem`, etc.) from `src/api/downloads.ts`. TypeScript catches shape mismatches at compile time.

**[Test count ~150-180]** Large test suite could become slow. → Mitigation: Playwright runs tests in parallel by default (per worker). MSW responses are instant (no network latency). Each test should complete in <1s. Total suite time expected: <30s locally, <2min in CI.

**[RuleSet Builder complexity]** The builder is the most complex view with multi-section forms, drag-and-drop rules, and live preview. → Mitigation: Focus on the critical paths (create, validate, save) and test rule manipulation as a separate concern. Don't aim for 100% coverage of every form field combination.
